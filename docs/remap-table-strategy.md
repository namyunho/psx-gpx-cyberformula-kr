# 리맵 표 기반 한글 운반 전략

## 결론

첫 한국어 대사 PoC에서 확인한 14x14 글리프 포맷과 화면 출력 경로는 유지한다.
다만 한글을 `0x5xxx` 또는 `0x7xxx` 같은 고상위 토큰으로 텍스트 스트림에 직접
넣어 렌더러 말단에서 가로채는 방식은 폐기한다. 이 게임은 렌더러가 토큰을 바로
글리프 인덱스로 쓰기 전에, 대사 블록별 표시 구조와 리맵 표를 한 번 더 거친다.

새 전략은 다음과 같다.

1. 디스크에는 전체 한글 글리프 팩을 Track 1 말미 `LBA 255811..255960`에 둔다.
2. 런타임에는 현재 화면 또는 텍스트 블록의 한글만 작은 캐시에 적재한다.
3. 텍스트 본문에는 엔진이 이미 처리하는 작은 로컬 토큰을 배정한다.
4. 그 로컬 토큰이 가리키는 블록별 리맵 표 또는 표시 버퍼 항목을 한글 캐시 슬롯에
   연결한다.

즉, 글리프 저장 공간 결정은 유지하고, 인코딩 운반 계층만 "고상위 최종 토큰"에서
"엔진 네이티브 로컬 토큰 + 리맵 표"로 바꾼다.

## 관찰 근거

첫 대사 화면에서 `ALLBIN.BIN + 0x54`는 런타임 `0x800A8054`에 적재된다. 그러나
렌더러 직전의 현재 토큰 포인터는 이 원본 대사 RAM이 아니라 `0x8001425A` 주변
구조를 가리켰다. 또한 `0x80061158`은 `0x8001426C` 주변을 가리켰고, 이 구조의
첫 word는 원본 대사 주소 `0x800A8054`였다.

렌더러 부근에서는 다음 흐름이 확인됐다.

```text
0x800327A8..0x800327D8 부근:
  현재 표시 구조에서 토큰을 읽음
  0x80061158을 통해 블록별 기준 구조를 얻음
  기준 구조 + token * 2를 읽어 최종 글리프 ID 또는 관련 값을 얻음
```

이 때문에 원본 텍스트에 없는 `0x5xxx`/`0x7xxx` 대역을 단순히 넣는 것은
부족하다. 고상위 값이 원본 RAM에는 남아도, 렌더러에 도착하기 전에 이름 변수
확장이나 블록별 리맵 계층에서 다른 의미로 해석된다.

## 폐기한 가정

`0x5xxx`는 대표 텍스트 구간에서 미사용이므로 안전한 한글 prefix라는 가정은
화면 검증에서 반증됐다. 해당 대역은 이름/변수 표시 또는 기본 이름 확장 경로와
충돌해 한자 `司馬`가 반복 표시됐다.

`0x7xxx`는 `0x5xxx` 충돌을 피할 예비 대역이라는 가정도 반증됐다. 원본 대사 RAM
`0x800A8054`에는 `0x7000..0x7011`이 남았고, 훅 코드와 캐시 바이트도 런타임에
보존됐지만, 화면에는 한글이 아니라 일부 구두점만 표시됐다. 이는 렌더러 말단
훅만으로는 한글 토큰을 운반할 수 없다는 증거다.

DuckStation 저장 상태도 주의한다. 에뮬레이터 save state는 이전 빌드의 RAM을
그대로 복원하므로 패치 검증에 쓰지 않는다. 깨끗한 부팅 뒤 게임 내부 메모리카드
로드는 사용할 수 있다.

## 다음 PoC

다음 PoC는 화면 표시를 다시 반복하기 전에, 변환 경로를 짧게 계측하는 것을 목표로
한다.

1. `ALLBIN.BIN + 0x54`의 첫 대사 토큰들이 `0x8001425A` 주변 표시 구조로 복사 또는
   변환되는 생산자 코드를 찾는다.
2. `0x8001426C` 주변 리맵 표의 크기, 엔트리 형식, 원본 토큰과 최종 출력값의
   대응을 첫 대사 34토큰에 대해 표로 남긴다.
3. 첫 대사의 한글 18자만 대상으로, 엔진이 받아들이는 작은 로컬 토큰을 배정하고
   리맵 표 또는 표시 버퍼를 패치해 한글 캐시 슬롯으로 연결한다.

통과 기준은 다음 세 가지다.

- 같은 첫 대사에서 원본 슬롯 덮어쓰기 없이 흰색 한글 두 줄이 표시된다.
- 괄호, 낫표, 말줄임표, 줄 경계, 페이지 대기 토큰이 기존처럼 동작한다.
- 리맵 표 수정 위치와 캐시 슬롯 배정이 빌드 스크립트의 데이터로 재현된다.
