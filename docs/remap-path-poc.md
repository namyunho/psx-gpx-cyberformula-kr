# 리맵/표시 버퍼 생성 경로 추적 PoC

> **역사적 PoC**: 이 문서의 “리맵 후보” 해석은 후속 IDA Pro/Ghidra 분석에서
> 폐기됐다. `0x8001426C`는 직접 텍스트 포인터 상태 필드이며 렌더러는 토큰
> 하위 12비트를 74바이트 글리프 레코드에 직접 적용한다. 현재 채택 경로는
> [`hangul-storage-encoding.md`](hangul-storage-encoding.md), 챕터 1 삽입
> 결과는 [`chapter01-disc-build.md`](chapter01-disc-build.md)를 따른다.

## 목표

고상위 한글 토큰 훅을 폐기한 뒤의 다음 목표는 첫 대사 원본 토큰이 렌더러 직전
표시 구조와 리맵 후보 테이블로 어떻게 넘어가는지 재현 가능한 보고서로 남기는
것이다. 이 PoC는 원본 ROM이나 BIOS를 수정하지 않고, DuckStation에서 캡처한
RAM 덤프와 추출된 실행 파일을 읽어서 파생 JSON만 생성한다.

## 추가한 도구

`scripts/trace_remap_path.py`는 두 가지를 수행한다.

- RAM 덤프에서 `[0x80061158]`, `[0x80060FA0]` 포인터 체인을 따라 첫 대사 상태를
  추출한다.
- `SLPS_019.58` 또는 원시 오버레이에서 감시 주소 주변을 참조하는 MIPS 명령을
  정적 스캔해 생산자 후보를 좁힌다.

기본 감시 주소는 다음과 같다.

| 항목 | 주소 |
|---|---:|
| 텍스트 상태 포인터 슬롯 | `0x80061158` |
| 표시 커서 포인터 슬롯 | `0x80060FA0` |
| 표시 커서 구조 후보 | `0x8001425A` |
| 텍스트 상태 구조 후보 | `0x8001426C` |
| 첫 대사 원본 RAM | `0x800A8054` |

## 로컬 덤프 검증 결과

이전 분석 폴더의 `work/ram-dialogue.bin`을 읽기 전용으로 사용해 다음 명령을
실행했다. 결과 JSON은 원본 덤프에서 파생된 분석물이므로 저장소에는 커밋하지
않고, 필요한 요약만 이 문서에 남긴다.

```powershell
python scripts/trace_remap_path.py `
  --ram C:\Users\namyunho\Documents\Codex\2026-07-12\mcpads-create-retro-game-kr-patch\work\ram-dialogue.bin `
  --binary C:\Users\namyunho\Documents\Codex\2026-07-12\mcpads-create-retro-game-kr-patch\work\disc1\SLPS_019.58 `
  --output work/remap-path/dialogue-remap-trace.json
```

확인된 포인터 체인:

| 항목 | 값 |
|---|---:|
| `[0x80061158]` | `0x8001426C` |
| `[0x80060FA0]` | `0x8001425A` |
| `[0x8001426C]` | `0x800A8054` |
| `u16[0x8001425A]` | `0x0022` |

`0x22`는 첫 화면의 34개 u16 토큰 수와 일치한다. 따라서 캡처 시점의
`0x8001425A`는 첫 페이지를 모두 소비한 표시 커서이고, `0x8001426C`의 첫 word는
현재 페이지의 시작 원본 주소 `0x800A8054`를 보관한다. 커서 값을 원본 주소에
적용하면 `0x800A8054 + 0x22 * 2 = 0x800A8098`이 되어 표시된 페이지 바로 뒤를
가리킨다.

첫 페이지 원본 토큰은 다음 34개로 재확인됐다.

```text
903F 000C 008C 004B 0088 0054 0058 0058
0082 006B 0052 0064 000B 03B7 0090 0072
FFFB 0000 00B5 0009 00D3 0001 000E 00AD
00A8 009A 00A4 00DC 00E2 00CA 00DD 000F
000D 8000
```

이 덤프에서 `0x8001426C + 4`부터의 u16 값은 원본 토큰 복사본이 아니라
상태 필드처럼 보인다. 그러므로 한글 운반 위치를 정하려면 “상태 구조 + 4”를
리맵 표로 가정해 패치하지 말고, 다음 런타임 계측에서 `0x800327A8..0x800327D8`
소비 지점의 기준 포인터가 어느 RAM 범위를 가리키는지 다시 캡처해야 한다.

## 정적 참조 스캔

기본 감시 주소를 정확 일치로 두고 `SLPS_019.58`을 스캔하면, 소비 지점 주변에서
두 전역 포인터를 직접 읽는 명령이 잡힌다.

| PC | 명령 word | 참조 |
|---|---:|---:|
| `0x800327B0` | `0x8C420FA0` | `[0x80060FA0]` |
| `0x800327B8` | `0x8C631158` | `[0x80061158]` |
| `0x800327E0` | `0x8C420FA0` | `[0x80060FA0]` |
| `0x800327E8` | `0x8C631158` | `[0x80061158]` |
| `0x800328B8` | `0x8C420FA0` | `[0x80060FA0]` |
| `0x800328C0` | `0x8C631158` | `[0x80061158]` |

이 결과는 `0x800327A8..0x800328C0` 일대가 렌더러 직전 변환 상태를 소비하는
핵심 관측 지점임을 다시 확인한다. 또한 `0x80039BF8`과 `0x80039C70`에는 각각
`0x80060FA0`, `0x80061158`로 쓰는 명령이 있어, 다음 정적 분석에서는 이 주변을
상태 구조 생산자 후보로 먼저 본다.

따라서 다음 계측은 다음 순서로 진행한다.

1. DuckStation을 첫 대사 직전의 깨끗한 부팅 상태로 멈춘다.
2. `0x800327A8..0x800327D8` 소비 지점에서 `v0`와 `[0x80061158]` 주변 0x80바이트를
   짧게 덤프한다.
3. 같은 프레임에서 `0x8001425A`, `0x8001426C`, 원본 페이지 시작 주소, 소비 지점
   기준 포인터를 함께 기록한다.
4. 소비 지점 기준 포인터가 확인되면 작은 로컬 토큰을 원본 슬롯 덮어쓰기 없이
   한글 캐시 슬롯으로 연결하는 최소 패치 위치를 다시 결정한다.

## 통과 기준

이번 PoC의 통과 기준은 화면 표시가 아니라 추적 기준선 확정이다.

- 첫 대사 34토큰과 표시 커서 `0x22`의 관계를 재현 도구로 확인했다.
- 상태 구조의 첫 word가 페이지 끝 원본 주소임을 확인해 이전 가정을 보정했다.
- `0x8001426C + 4`를 리맵 표로 즉시 패치하면 안 된다는 음성 기준을 문서화했다.
- 다음 런타임 계측에서 캡처해야 할 주소와 값이 구체화됐다.
