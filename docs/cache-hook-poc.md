# 고상위 한글 캐시 훅 PoC (폐기)

## 목표

첫 한글 대사 PoC는 원본 일본어 글리프 슬롯을 임시로 덮어썼습니다. 이번 PoC의
목표는 한글 토큰을 고상위 대역으로 운반하고, 렌더러 훅이 해당 토큰만 한글 캐시
베이스에서 읽도록 만드는 것이었습니다.

이 가정은 DuckStation 화면 검증에서 반증되어 폐기했습니다. 정적 빌드, 런타임
RAM 생존, 원본 대사 RAM의 토큰 보존은 모두 확인했지만, 한글이 화면에 도달하지
못했습니다. 이 문서는 같은 길을 다시 반복하지 않기 위한 실패 기록입니다.

## 폐기 결론

`0x5xxx` 토큰은 화면에 한글 대신 한자 `司馬`가 반복 표시되어 폐기했습니다.
대표 텍스트 구간의 정적 출현 수가 0이어도, 이 대역은 이름/변수 표시 또는 기본
이름 확장 경로와 충돌합니다.

`0x7xxx` 토큰은 원본 대사 RAM `0x800A8054`에는 남았지만 화면에는 구두점 일부만
표시되어 폐기했습니다. 이는 원본 대사 토큰이 렌더러까지 직접 전달되지 않고,
`0x8001425A` 주변 표시 구조와 `0x8001426C` 주변 리맵 표를 먼저 거친다는 증거입니다.

따라서 이 PoC의 후속 작업은 더 이상 렌더러 말단 훅 보정이 아니라
[`docs/remap-table-strategy.md`](remap-table-strategy.md)의 리맵 표 기반 전략입니다.

## 최종 실패 변형

| 항목 | 값 |
|---|---:|
| 훅 설치 위치 | `0x80032804` |
| 훅 코드 위치 | `0x8005BB18` |
| 한글 캐시 위치 | `0x8005B5E4` |
| 캐시 글리프 수 | 18 |
| 한글 토큰 범위 | `0x7000..0x7011` |

마지막 변형은 이미 리맵 이후로 보이는 `0x80032804`에 설치했습니다. 현재
리맵 표 주소 범위가 `0x800B6054..0x800B6078`일 때만 한글 캐시 베이스를
선택하도록 시도했지만, 화면 검증은 실패했습니다.

정적 디스어셈블 확인:

```text
0x80032804: j       0x8005bb18
0x80032808: nop
0x8003280C: nop

0x8005BB18..0x8005BB84:
  v0가 0x800B6054..0x800B6078 안의 짝수 주소인지 확인
  범위 안이면 v1 = (v0 - 0x800B6054) / 2
  a0 = 0xA005B5E4
  원본의 andi/sll/addu를 보상 실행하고 0x80032810으로 복귀
```

## 대사 토큰

첫 대사는 다음 한국어 문장을 사용합니다.

```text
（드디어 여기까지 왔다…
꿈의 팀 「스고 그랑프리」）
```

최종 실패 변형에서는 한글 18자를 첫 등장 순서대로 `0x7000..0x7011`에
배정했습니다. 공백은 기존
빈 글리프 `0x04CD`를 사용하고, 괄호·낫표·말줄임표는 원본 글리프를 유지합니다.

```text
드=0x7000, 디=0x7001, 어=0x7002, 여=0x7003, 기=0x7004, 까=0x7005,
지=0x7006, 왔=0x7007, 다=0x7008, 꿈=0x7009, 의=0x700A, 팀=0x700B,
스=0x700C, 고=0x700D, 그=0x700E, 랑=0x700F, 프=0x7010, 리=0x7011
```

## 재현 빌드

```powershell
$env:PYTHONPATH = "work/pydeps-current;work/pydeps"
python scripts/build_cache_hook_poc.py `
  --slps work/disc1/SLPS_019.58 `
  --allbin work/disc1/ALLBIN.BIN `
  --ttf font/font-12345a7f7565e4fe.ttf `
  --intensity 1 `
  --output-dir work/cache-hook-poc/files `
  --track1 "roms/Future GPX Cyber Formula - Aratanaru Chousensha (Japan) (Disc 1) (Track 1).bin" `
  --track-output work/cache-hook-poc/disc1-cache-hook-track1.bin `
  --source-cue "roms/Future GPX Cyber Formula - Aratanaru Chousensha (Japan) (Disc 1).cue" `
  --cue-output work/cache-hook-poc/disc1-cache-hook.cue `
  --allow-invalid-edc
```

최종 실패 변형 산출물:

| 산출물 | SHA-256 |
|---|---|
| PoC `SLPS_019.58` | `9D0986510EC455AF10C45EF9E4E4BCFE8B072172CAD855250479EA36B5AF71F1` |
| PoC `ALLBIN.BIN` | `76D5BF7E93A2AEEF18290ADAC4AF97A336973F4888554A768EADB94E22BF3F81` |

변경된 raw 섹터는 LBA 30, 111, 112, 9919입니다. 이 PoC 이미지는 변경 섹터의
EDC/ECC를 아직 재계산하지 않으므로 **DuckStation 검증 전용**입니다. 실기,
CD-R, ODE 또는 배포 빌드에는 사용하지 않습니다.

## 통과한 검증과 실패한 검증

- 훅 설치 위치의 원본 바이트를 검증한 뒤에만 패치합니다.
- 실제 CLI 빌드는 원본 `SLPS_019.58`의 SHA-256이
  `0CBDA75255E7F9EDBB758EE8B815082C3DD167E7E0E709A5526C17653014FAB9`일 때만
  패치합니다.
- `0x7000..0x7011` 토큰은 원본 대사 RAM `0x800A8054`에 그대로 적재됐습니다.
- 훅 코드와 캐시 글리프는 런타임 RAM에서 파일 바이트와 일치했습니다.
- `scripts/psx_font.py`로 캐시 글리프 18자를 렌더링해 자형을 확인했습니다.
- 화면 검증은 실패했습니다. 한글이 보이지 않고 일부 구두점만 표시됐습니다.

## 런타임 공간 검증

처음 고른 제로 채움 후보는 부팅 뒤 보존되지 않았습니다.

| 후보 | 판정 |
|---|---|
| 훅 `0x8005A000`, 캐시 `0x80059800` | 부팅 뒤 0으로 지워져 폐기 |
| 훅 `0x8005A800`, 캐시 `0x80059850` | 부팅 뒤 0으로 지워져 폐기 |
| 훅 `0x8005BB18`, 캐시 `0x8005B5E4` | DuckStation GDB에서 파일 바이트와 RAM 바이트 일치 확인 |

현재 후보는 원본상 0으로 빈 code cave가 아니라 런타임에 보존되는 비제로 영역을
임시로 덮어쓰는 실험입니다. 따라서 self-boot 훅 경로 확인에는 유효하지만, 이
주소를 최종 저장 공간으로 승격하지는 않습니다. 본 구현에서는 디스크 말미 폰트
팩을 별도로 읽어 안전한 캐시 RAM에 적재하는 경로를 확정해야 합니다.

## 후속 조치

이 PoC는 본 구현 후보로 승격하지 않습니다. 남길 것은 두 가지뿐입니다.

- 고상위 대역의 정적 미사용 여부는 안전한 텍스트 운반을 증명하지 않는다.
- 다음 PoC는 `ALLBIN.BIN + 0x54` 토큰이 `0x8001425A` 표시 구조와
  `0x8001426C` 리맵 표로 바뀌는 생산자 경로를 추적해야 한다.
