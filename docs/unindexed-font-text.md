# 추가 순차·색인·저장 글꼴 문자열

## 목적과 판정

직접 포인터를 중심으로 만든 기존 workset 네 종류 밖의 물리 영역을 다시
검사해, 게임 글꼴로 출력되는 일본어 스트림 806개를 보호 workset과 한국어
번역 정본으로 분리했다. 그래픽 버튼·라벨처럼 이미지에 새겨진 문자는 이
범위에 포함하지 않는다.

이 806개는 단순히 디코딩 가능한 바이트를 모두 채택한 결과가 아니다.
IDA Pro와 Ghidra에서 본문 렌더러가 `base + cursor * 2`를 계속 읽고
`0x8000` 뒤에도 커서를 유지하는 구조를 교차 확인했다. 경기·미니게임·저장
overlay에서는 같은 렌더 문법을 쓰는 연속·색인 풀과 인접 소비자 계열을
확인했다. 다만 모든 분기에서 어느 색인으로 진입하는지와 재삽입 후 실행
안정성은 아직 전수 검증하지 않았으므로 배포·빌드 적격으로 판정하지 않는다.

## 모집단

기존 직접 대사, 무포인터 페이지, 특수 화면과 UI workset이 차지하는 물리
범위를 먼저 마스킹한 뒤, 남은 gap에서 primary 글꼴 토큰과 유효 종료 토큰을
가진 후보만 찾았다. 발견 후보 795개를 원본 바이트·주변 구조와 대조해 이진
데이터 오탐 59개를 고정 제외했다.

| 분류 | unit | 항목 |
|---|---|---:|
| 순차 이벤트 페이지 | `u02..u19` | 295 |
| 색인·분기 경기 페이지 | `u28`, `u30..u34` | 410 |
| 추가 미니게임 분기·결과 | `u38` | 74 |
| 저장·불러오기 메시지 | `u39` | 27 |
| **합계** |  | **806** |

추가된 `u28` 8개는 직접 참조되는 `0x0F34`의 `FFFF` 페이지 직후
`0x0F72..0x10C2`에 연속된 `8000` 종료 페이지다. 화자·음성 제어 셸이
정상이고 다음 페이지로 fall-through하는 혼합 종료 스트림이므로 채택했다.
기존 추출기가 `u21..u34`에는 `FFFF/D003`만 있다고 가정해 누락했던 범위다.

`u30..u34 +0x7190..+0x7490`에는 최종전 장면 14페이지가 5개 overlay에
바이트 단위로 동일하게 들어 있다. 총 70개 물리 스트림이며, 세 overlay의
14개 시작 주소 참조와 사용자가 제공한 실행 화면으로 실제 소비를 확인했다.
이 구간은 일반 `0x8000` 휴리스틱에 넣지 않고 정확한 범위·페이지 경계·풀
SHA-256을 모두 검증한 뒤에만 채택한다. 번역은 각 물리 복사본에서 따로 만들지
않고 의미가 같은 `u19/ref0004..ref0017` 14개를 명시적으로 참조한다. 한 페이지의
일본어 말줄임표 차이는 검토된 구두점 변형으로 기록하며, 각 overlay의 화자·
이름·음성·종료 제어 셸은 자체 원본 바이트를 유지한다.

### 짧은 구두점·반응 페이지 재감사

일본어 글리프가 2개 이상이어야 한다는 과거 탐색 조건 때문에 11개 물리
페이지가 더 빠져 있었다. `u04 +0x00D86`, `u16 +0x0127A/+0x015B2`,
`u18 +0x01F72`는 인접 순차 페이지의 fall-through로, `u28 +0x01008`은
`u28 +0x4220`의 절대 포인터로 소비가 확인됐다. `u30/u31 +0x05630`,
`u32/u34 +0x0523C`, `u33 +0x0523C/+0x05630`의 여섯 `…。`는 형제
overlay에서 직접 참조되는 `u30/embedded_race/e0040`과 바이트가 같은 경기
페이지다. 여섯 복사본은 이 정본 번역을 명시적으로 공유한다. 이 주소들은
일반 휴리스틱에 맡기지 않고 시작 주소와 소비 근거를 고정 목록으로 검증한다.

59개 오탐 주소와 `u33/u34`의 두 시작 보정은
`scripts/extract_unindexed_font_text.py`에 명시되어 있다. 후보 수,
오탐 수, 전체 수와 unit별 수량이 하나라도 달라지면 추출기가 실패한다.
휴리스틱 결과가 조용히 새 정본으로 승격되는 일은 없다.

## 산출물과 재생성

```bash
.venv/bin/python scripts/extract_unindexed_font_text.py
.venv/bin/python scripts/build_unindexed_font_translation.py
.venv/bin/python scripts/dialogue_layout_editor.py --check
```

| 파일 | 역할 |
|---|---|
| `work/translations/disc1-unindexed-font-text.json` | 원본 raw·u16 토큰·제어토큰·일본어·물리 주소를 보존한 806개 workset |
| `data/translations/disc1-unindexed-font-ko-manual.json` | 새 원문과 문맥 충돌·표기 교정에 대한 수동 한국어 결정 |
| `data/translations/disc1-unindexed-font-ko.json` | 안정 ID 순서로 완성한 806개 한국어 초벌 번역 정본 |

전체 806개 중 기존 정본과 공백을 제외한 일본어가 같고 한국어 결정도 하나뿐인
항목은 그 결정을 재사용했다. 새 일본어는 중복을 합치면 298종이며, 같은
일본어에 기존 한국어가 여러 개였던 물리 항목 14개는 자동 선택하지 않고
문맥별 결정을 요구했다.

생성된 정본의 출처는 다음과 같다.

| 출처 | 항목 |
|---|---:|
| 새 원문·정확한 문맥·표기 수동 번역 | 329 |
| 기존 번역 충돌 수동 해소 | 10 |
| 동일 일본어의 기존 결정 재사용 | 356 |
| 동일한 새 일본어 결정 재사용 | 35 |
| 명시적 물리 미러·별칭 (`u19` 최종전 70 + 짧은 경기 6) | 76 |
| **합계** | **806** |

원문, 안정 ID, raw 바이트와 제어토큰은 번역 JSON에서 다시 만들지 않는다.
편집기는 보호 workset과 한국어 정본을 안정 ID로 결합하고, 수정할 수 있는
필드는 `translations[].ko`뿐이다.

## 번역·표시 검증

- 기존 캐릭터·팀·머신 용어집 표기를 유지했다.
- 이름 토큰 `{name:surname}`, `{name:given}`은 정본에 그대로 보존한다.
- 806개 모두 각 원본 레이아웃의 행 수와 줄당 17글리프 안에 들어간다.
- 빈 한국어, 안정 ID 누락·중복과 원본 순서 변경은 0개다.
- 같은 일본어에 서로 다른 기존 한국어가 대응하는 23개 물리 항목은 안정 ID
  수동 결정을 거쳐 재현 가능하게 고정한다.
- 최종 통합 빌드는 primary 1,229슬롯 중 1,041자를 매핑한다. 영문·숫자·
  특수문자 보호 슬롯을 포함한 점유를 제외하면 162슬롯이 남는다.
- 영문·숫자·특수문자 보호 영역을 한글 할당 대상으로 바꾸지 않는다.
- 통합 편집기는 독립 번역 730개를 포함해 총 7,059행을 표시한다. 최종전 물리
  미러 70개와 짧은 경기 미러 6개는 별도 편집 행을 만들지 않고 각 정본 행에서
  함께 생성해 복사본 간 표기 충돌을 막는다.

현재 번역 상태는
`needs-independent-and-runtime-review`다. 외부 독립 언어 검수 도구를
호출하려 했으나 로컬 Gemini Code Assist 개인 계정 클라이언트가 지원 종료
오류를 반환해 교차검수를 완료하지 못했다. 따라서 이 사실을 숨기거나
“검수 완료”로 바꾸지 않는다.

## 정적 재삽입

`scripts/build_dialogue_chapter_patch.py --include-reviewed-unindexed-story`
는 `u02..u19` 순차 페이지 295개와 `u28`, `u30..u34` 경기 페이지 410개를 기존
직접·무포인터 대사와 같은 unit 공용 arena에 넣는다. 원본 전체 해시에 대해
고정한 절대 참조 카탈로그를 다시 대조하고, 원본 엔트리 내부 `+2`를 가리키는
제어 셸 앵커도 소유 엔트리와 함께 재배치한다.

### u11 블랙잭 무작위 상대 참조

2026-08-08 정적 분석에서 `1회전 내 상대는…` 뒤의 무작위 상대 발표문은
일반 32비트 포인터 표가 아니라 u11 실행 코드의 `LUI+ADDIU` 조합으로 직접
주소를 만든다는 사실을 확인했다. 7분기는 카자미·구데리안·하이넬·카가·신죠·
부츠홀츠·메구 발표문을 가리킨다. 기존 unit 공용 arena 재배치는 저장된 절대
포인터만 갱신했으므로 이 즉시값들은 원본 주소에 남았고, 선택된 상대에 따라
이름이 비거나 잘못된 스트림을 읽어 크래시할 수 있었다.

빌더는 이제 u11의 정확한 7개 명령어 쌍과 원본 대상·엔트리 내부 `+2` 앵커를
고정 검증하고, 재배치된 위치에 맞춰 MIPS signed-low 보정을 포함한 상·하위
즉시값을 다시 기록한다. 최종 파일 빌드에서는 7개 계산 주소, 한국어 문자열과
각 `0x8000` 종료를 모두 재검증했다. 이 결과는 정적 수정 완료이며 무작위 7분기
전수 실행은 별도 사용자 검증 대상으로 남긴다.

`scripts/build_unindexed_font_patch.py`는 특수 화면 정적 주입 뒤에 다음 두
범위를 결합한다.

- `u38` 74개: 기존에 시작 주소가 검증된 미니게임 페이지를 앵커로
  삼아 바로 뒤의 연속 페이지를 같은 구간 안에 재패킹한다.
- `u39` 27개: 연속 저장·불러오기 메시지 표의 첫 시작과 전체 바이트 용량을
  유지한 채 원본 순서로 재패킹한다.

요리 결과 스트림은 별도로 원본 페이지 수를 검증한다. `cooking_taste_start`와
반응 18종의 각 직접 참조 주소는 움직이지 않으며, 모든 `0x8000` 후속 페이지를
원본 순서대로 다시 인코딩하고 마지막에 `0xFFFF`를 정확히 하나 기록한다.
남는 용량은 종료 토큰 뒤에서만 0으로 채운다. 이 과정에서 일본어 판정 기준을
충족하지 못해 빠졌던 구두점 전용 페이지 `u38:0x1DA50`의 `…。`도 명시적 검토
항목으로 편입했다. 이전 빌드의 큰 선행 공백은 종료 토큰 없이 남은 0 워드,
반응 뒤 파편 글자는 짧아진 첫 페이지 뒤에 남아 있던 원본 일본어였다.

기존 725개 통합판과 u11 블랙잭 참조 수정은 2026-08-08 Disc 1·2 개발 이미지에
반영했다. 두 디스크 모두
1,135개 변경 sector의 Expected Write와 Mode 2/Form 1 EDC·P/Q ECC가
일치했고, 완성 CUE에서 다시 추출한 파일 해시도 파일 빌드와 일치했다. 이 정적
성공은 아직 모든 색인·분기에서 실제 소비됐다는 실행 증거는 아니다.

최종전 미러 70개를 더한 795개판은 정적 추출·번역·unit 공용공간 재배치와
전체 참조 카탈로그 검증을 통과했다. 실제 최종전 재현은 새 이미지에서 다시
확인해야 한다.

후속 806개판은 위 11개 짧은 페이지를 고정 목록과 소비 근거로 추가했다.
Disc 1·2에서 각각 1,138개 변경 sector의 Expected Write, Mode 2/Form 1
EDC·P/Q ECC와 파일 재추출 해시 검증을 통과했다. Track 1 SHA-256은 Disc 1
`bc3c4344c2d0f29e454e2b7e94a59ef80cc5878cea509e0a44d66a816aba5603`, Disc 2
`7016164a8d7e43d81be12e4bccc4ccaeda47691d46b166702af252d37c0ed7f9`다.
이 해시는 로컬 회귀 식별값이며 11개 새 경로의 실행 검증은 별도로 남는다.

2. 저장·불러오기 성공·실패·덮어쓰기·데이터 없음 경로를 전수 실행한다.
3. 독립 언어 검수와 사용자 화면 검수를 통과한 뒤에만 배포 적격으로
