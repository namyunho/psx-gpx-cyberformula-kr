# PS1 글꼴 포맷 분석

## 확정 결과

글꼴은 표준 TIM 이미지가 아니라 `START.BIN` 안의 고정 길이 압축 글리프
테이블 두 개입니다.

| 항목 | primary dialogue | alternate UI |
|---|---:|---:|
| START unit | 2 | 40 |
| 파일 기준 주소 | `+0x1A000` | `+0x3D1800` |
| RAM 기준 주소 | `0x80014A00` | `0x80185000` |
| scheduled 크기 | 92,160 | 124,928 |
| 74바이트 record 용량 | 1,245 + 30바이트 | 1,688 + 16바이트 |
| 실제 정의 slot | 1,229 | 1,484 |
| 마지막 정의 index | `0x4CC` | `0x5CB` |

두 표에 공통인 포맷:

| 항목 | 값 |
|---|---:|
| 글리프 크기 | 14×14픽셀 |
| 픽셀 깊이 | 3bpp, 값 0~7 |
| 글리프당 크기 | 74바이트 |
| 픽셀 비트 순서 | little-endian, LSB 우선 |
| 글리프 선택 | `(token & 0x0FFF) * 74` |

14×14픽셀은 196픽셀이며 3bpp로 588비트가 필요합니다. 따라서 한 글리프는
74바이트이고 마지막 4비트는 패딩입니다.

## 실행 코드 경로

- `0x80032704`: 현재 텍스트 토큰 선택, 글리프 인덱스 계산, 화면 좌표 계산
- `0x80032434`: 74바이트 3bpp 글리프를 14×14 출력 영역으로 해제
- `0x8003259C`: 같은 입력 포맷을 사용하는 다른 출력 폭의 변형 해제 루틴

`0x80032704`는 일반 대사 상태에서 `0x80014A00 + index * 74`를 글리프
원본으로 사용하고, `dword_80061140 & 0x2000`이면 `0x80185000`의 alternate
표를 선택합니다. `0x80032434`는 3비트 픽셀을 순서대로 읽어 게임의 4bpp 작업
표면에 배치합니다.

`START.BIN + 0x1A000`과 `0x80014A00`의 대응은 Disc 1 대사 시점 RAM 덤프와
파일 조각의 바이트 일치, 그리고 로더 배치 차이 `-0x5600`으로 확인했습니다.

## 화면 교차 검증

초기에는 `data/glyph-map.json`의 29개 화면 증명 토큰을 이 포맷으로 직접
렌더링해 괄호, 줄임표, 가나와 한자 `憧`을 교차 검증했습니다. 이후 사용자가
실제 게임 색상에 맞게 정규화한 두 아틀라스로 primary 1,229자와 alternate
1,484자의 전체 대응표를 완성했습니다. 두 표는 기호 배치와 수록 문자가 다르므로
`primary`와 `alternate` scope를 분리해 사용합니다.

재현 명령:

```powershell
$env:PYTHONPATH = "work/pydeps"
python scripts/psx_font.py work/disc1/START.BIN `
  --offset 0x1A000 `
  --glyph-map data/glyph-map.json `
  --glyph-table primary `
  --output work/font-known.png
```

## 한국어 PoC에 주는 의미

한국어 PoC는 다음 최소 경로로 만들 수 있습니다.

1. 사용하지 않는 글리프 슬롯을 확정한다.
2. 14×14, 3bpp 한글 글리프를 `pack_glyph()`로 인코딩한다.
3. 해당 슬롯의 74바이트를 교체한다.
4. 시험 대사의 토큰을 새 슬롯 번호로 바꾼다.
5. 수정된 파일을 별도 작업 이미지에 재삽입해 에뮬레이터에서 검증한다.

## primary 빈 슬롯과 현재 적재 한계

대사 시점 RAM 덤프에서 `START.BIN + 0x1A000`과 `0x80014A00`의 연속 일치는
`0x16393`바이트입니다. 글리프 `0x4CD`는 `START.BIN + 0x30342..0x3038B`,
RAM `0x8002AD42..0x8002AD8B`에 해당하며 74바이트 전체가 0이고 연속 일치
범위 안에 들어갑니다. 다음 데이터와의 여유는 7바이트뿐입니다.

따라서 `0x4CD` 한 슬롯은 기존 첫 가시성 PoC에 사용할 수 있었습니다.
`0x4CE`부터는
대사 시점에 실행 코드와 겹치므로 빈 슬롯으로 간주하지 않습니다. 다른 시점의
RAM 덤프에서는 더 긴 범위가 남아 있어도, 가장 좁은 대사 시점의 적재·덮어쓰기
범위가 현재 안전 상한입니다.

파일 안에서 뒤가 0이라는 사실은 runtime에서 안전한 상주 슬롯이라는 뜻이 아니다.
alternate의 15,112바이트 trailing zero도 같은 이유로 즉시 한글 공간으로 쓰지
않는다.

이 결과는 전체 한국어 글리프 수용량을 해결하지 않습니다. 본 구현에는 폰트
저장 위치 재배치, 로더 크기 확장 또는 별도 한글 글리프 공급 경로가 필요합니다.

## 한국어 확장 전략 결정

대사 렌더러는 기본적으로 `0x80014A00`을 폰트 베이스로 쓰지만, 조건에 따라
`0x80185000`을 베이스로 쓰는 분기도 이미 가지고 있습니다. 그러나 대사 시점의
`0x80185000` 이후 RAM은 이미 데이터가 있어 전체 한글 상주 영역으로 쓰지
않습니다.

전체 2,350자 Galmuri11 글리프는 `2350 * 74 = 0x2A74C`바이트가 필요합니다.
현재 확인된 대사 시점의 최대 연속 0 채움 구간은 이보다 작으므로, 전상주 테이블
대신 Disc 1 Track 1 말미의 `LBA 255811..255960` 150섹터에 저장한 폰트 팩과
화면 단위 RAM 캐시를 사용합니다.

초기에는 한글 텍스트 토큰을 `0x5xxx` 대역으로 예약하고 렌더러 훅에서
`token & 0x0FFF` 마스크 직전에 분기하려 했습니다. 그러나 화면 검증에서
`0x5xxx`는 이름/변수 경로와 충돌했고, `0x7xxx`는 렌더러 직전 리맵 계층에서
사라졌습니다. 따라서 글리프 포맷과 캐시 전략은 유지하되, 인코딩 운반은 엔진
네이티브 로컬 토큰과 리맵 표를 사용하는 방향으로 바꿉니다. 세부 계산과 근거는
[`docs/hangul-storage-encoding.md`](hangul-storage-encoding.md)에 기록합니다.
