# 캐릭터 이름과 고정 주인공명

이 문서는 Disc 1의 이름 입력 화면, 이후 주인공명 재표시, 대사창 화자명
테이블을 서로 다른 소비자로 구분하고, 한국어 이름을 원본 안전 영역 안에서
삽입하는 기준을 기록한다. 2026-07-27 정적 패치와 디스크 재추출 검증을
완료했고, 사용자가 실제 게임에서 고정 이름과 용어집 표기가 정상 등장하는
것을 확인했다.

## 결론

- 주인공의 기본 이름은 **성 `시바`, 이름 `세이치로`**로 고정한다.
- 원본의 성 3칸·이름 3칸을 합친 6개 런타임 글리프 record를 늘리지 않고
  **성 2칸·이름 4칸**으로 재분할한다.
- 이름 화면용 한글 6자는 alternate UI font의 검증된 zero tail
  `0x5CC–0x5D1`에 넣는다.
- 대사창 화자명 34개는 `SLPS_019.58`의 원본 문자열 영역 284바이트 안에서
  다시 묶는다. 한국어 결과는 208바이트이고 76바이트가 남는다.
- 고정 슬롯은 넘칠 때 자르지 않는다. 성·이름 길이, 화자명 6글리프 한도,
  문자열 영역 총량 중 하나라도 넘으면 빌드를 실패시킨다.

## 서로 다른 세 소비자

이름 관련 화면이 같아 보여도 저장·렌더 경로는 하나가 아니다.

| 소비자 | 데이터 | 패치 방침 |
|---|---|---|
| 이름 입력 화면 | unit 40 기본 코드와 74바이트 scratch glyph | 기존 6 record를 2+4로 재분할 |
| 이후 주인공명 표시 | 메인 실행 파일의 연속 u16 가상 글리프 코드 6개 | 성 `[0,1]`, 이름 `[2,3,4,5]` |
| 대사창 화자명 | `SLPS_019.58`의 34개 `{length, pointer}` record | 원본 284바이트 문자열 영역 안에서 재패킹 |

따라서 이름 입력 화면만 고치거나 화자명 문자열만 바꾸면 나중의 이름 재표시가
어긋날 수 있다. 세 경로를 한 빌드에서 함께 검증한다.

## 이름 입력기의 2+4 안전 레이아웃

IDA Pro의 instruction·xref와 Ghidra의 함수 제어 흐름을 교차 대조했다.
unit 40은 `ALLBIN.BIN + 0x151800`에 있고 `0x80098000`에 적재된다.

| 항목 | 원본 | 한국어 |
|---|---:|---:|
| 성 scratch 시작 | `0x8002AD8C` | 동일 |
| 성 record 수 | 3 | 2 |
| 이름 scratch 시작 | `0x8002AE6A` | `0x8002AE20` |
| 이름 record 수 | 3 | 4 |
| 전체 끝 주소 | `0x8002AF48` | 동일 |
| 추가 런타임 바이트 | 0 | 0 |

한 글리프 record는 74바이트다. 원본 이름 시작점은
`0x8002AD8C + 3×74 = 0x8002AE6A`이고, 한국어 이름 시작점은
`0x8002AD8C + 2×74 = 0x8002AE20`이다. 어느 쪽도 6개 record의 끝
`0x8002AF48`을 넘지 않는다.

메인 실행 파일의 `sub_80039D24`는 이름용 가상 글리프 코드
`0x4CE–0x4D3` 여섯 개를 연속으로 준비한다. 원본은 이름 코드 배열을 상태
offset `+0x38`에서 시작하지만 한국어판은 `+0x36`으로 한 u16 앞당긴다.
초기화 루프가 전역 포인터 세 개를 만들지만 실제 이름 소비자는 첫 전역
`0x800615F8`의 값을 **연속 u16 배열의 base**로 읽는다. 뒤의 두 전역
`0x800615FC`, `0x80061600`을 직접 읽는 xref는 없다.
`sub_80032704`와 `sub_800329B8`은 이 base에 `index×2`를 더하고,
`0x80061180`의 이름 길이만큼 반복하므로 성 2개 뒤의 연속 4개를 이름으로
읽을 수 있다.

base만 한 칸 앞당기면 초기값과 clear가 아직 3글리프에 머무르므로 다음
메인 실행 파일 수정도 함께 적용한다.

- `sub_8003A434`의 이름 코드 clear 반복 횟수: 3 → 4
- 원래 성의 세 번째 초기값 `0x4D0`은 새 이름 첫 글리프로 유지
- 기존 이름 초기값 `0x4D1`, `0x4D2`, `0x4D3`의 store offset을 각각
  `+0`, `+2`, `+4`에서 `+2`, `+4`, `+6`으로 이동

그 결과 상태 offset `+0x32..+0x3C`의 여섯 u16은
`0x4CE, 0x4CF | 0x4D0, 0x4D1, 0x4D2, 0x4D3`이 된다. 별도 7번째
글리프나 새 포인터는 필요하지 않다.

| 가상 글리프 | scratch 주소 | 역할 |
|---|---:|---|
| `0x4CE` | `0x8002AD8C` | 시 |
| `0x4CF` | `0x8002ADD6` | 바 |
| `0x4D0` | `0x8002AE20` | 세 |
| `0x4D1` | `0x8002AE6A` | 이 |
| `0x4D2` | `0x8002AEB4` | 치 |
| `0x4D3` | `0x8002AEFE` | 로 |

Ghidra로 패치된 실행 파일을 다시 디컴파일해 이름 clear가 4회이고, 기본값
store가 `DAT_800615f8 + 2/+4/+6`으로 이동한 것을 확인했다. IDA의 원본
xref에서는 `0x800615F8`만 이름 배열 base로 소비되고 뒤의 두 전역에는 직접
xref가 없었다.

unit 40의 기본 이름 원본은 다음 위치에 있다.

| 구성 | RAM | `ALLBIN.BIN` | 원본 | 한국어 코드 |
|---|---:|---:|---|---|
| 성 | `0x800A0714` | `0x159F14` | `司 馬 0 0` | `시 바 0 0` |
| 이름 | `0x800A071C` | `0x159F1C` | `誠 一 郎 0` | `세 이 치 로` |

alternate font에는 다음 고정 슬롯을 사용한다.

| 문자 | 코드 |
|---|---:|
| 시 | `0x5CC` |
| 바 | `0x5CD` |
| 세 | `0x5CE` |
| 이 | `0x5CF` |
| 치 | `0x5D0` |
| 로 | `0x5D1` |

`START.BIN + 0x3D1800`의 alternate font는 원본 정의 글리프가
`0x000–0x5CB`이고 뒤에 15,112바이트의 zero tail이 있다. 위 여섯
record는 첫 444바이트만 사용한다. 파일 뒤가 0이라는 사실만으로는 일반적인
상주 글꼴 공간이라고 판정할 수 없지만, 이 경우에는 이름 화면에서 쓰는
scheduled unit 40이 `0x80185000–0x801A3800`의 124,928바이트 전체를
적재한다. 마지막 추가 record는 `0x8019FEB4`에서 끝나므로 unit 경계까지
14,668바이트가 남는다. 이 여섯 슬롯은 이름 화면 소비자에만 배정하고 대사
primary font의 확장 공간으로 일반화하지 않는다.

## 대사창 화자명 테이블

`SLPS_019.58`의 문자열과 record는 다음 고정 영역에 있다.

| 항목 | 파일 범위·위치 | 런타임 |
|---|---:|---:|
| 문자열 영역 | `0x1FA50–0x1FB6C` | `0x8004F250–0x8004F36C` |
| 34개 record 표 | `0x1FB6C` | `0x8004F36C` |
| record 형식 | `u16 length, u16 zero, u32 pointer` | 8바이트 |

이 표는 인물명만의 목록이 아니다. 인물 외에 아스라다·네메시스 같은
머신/시스템명, 드라이버 A/B/C, 아나운스, 일동, `？？？`도 같은 화자명
소비자를 쓴다. 부분적으로 바꾸면 화면마다 일본어와 한국어가 섞이므로 34개
record를 모두 등록한다.

현재 한국어 표기는
[`disc1-character-names.json`](../data/translations/disc1-character-names.json)에
고정한다. 용어집에서 인물로 분류된 연결 항목은 모두 `approved`여야 한다.
머신·역할 항목은 기존 용어 후보와 표기가 정확히 맞아야 한다.

| 안전 조건 | 결과 |
|---|---:|
| record 수 | 34 |
| 개별 안전 한도 | 6글리프 |
| 한국어 최대 길이 | 5글리프 |
| 원본 문자열 용량 | 284바이트 |
| 한국어 사용량 | 208바이트 |
| 남는 원본 영역 | 72바이트 |

## 이름 등록 화면의 폰트 UI

`work/translations/disc1-ui.json`의 60개는 게임 전체 UI가 아니라 unit
`40`의 이름 등록 화면 글꼴 스트림이다. 이 중 문장·라벨인 4개만
`data/translations/disc1-ui-ko.json`에서 번역한다.

| 역할 | 수 | 처리 |
|---|---:|---|
| 한자 입력 팔레트 | 47 | 원본 보존 |
| 입력·확인 문구 | 2 | 한국어 |
| 가나·영문·숫자·기호 팔레트 | 6 | 원본 보존 |
| 이름·출신 라벨 | 1 | 한국어 |
| 출신 선택지 | 1 | 한국어 |
| 가상 주인공명 스트림 | 2 | 런타임 코드 보존 |
| 출신 표시 가변 버퍼 | 1 | 런타임 버퍼 보존 |

한국어 네 스트림은 원본의 1·3·4·6행 수와 `FFFB` 개수를 그대로
유지한다. primary 렌더러 세 스트림은 전체 대사 빌드의 정적 한글 맵을
공유하고, alternate 출신 선택지는 이름용 여섯 글리프 다음의 zero tail
`0x5D2..0x5DC`에 11글리프를 추가한다. 입력 팔레트 53개를 번역문으로
오인해 덮어쓰지 않으며, 가변 스트림 세 개도 런타임 소비를 보존한다.

현재 정적 검사는 네 스트림의 원본 슬롯, 행 경계, 제어 셸과 alternate
zero tail을 통과했다. 상태는
`static-translation-complete-runtime-review-required`이며 이름 등록의
각 입력 모드·출신 선택을 전부 눌러 보는 실행 검토가 남아 있다.

## 재현 빌드

먼저 대사·primary font 파일 빌드를 만든 뒤 이름과 UI 패치를 차례로 겹친다.

```bash
.venv/bin/python scripts/build_character_name_patch.py \
  --file-build-dir work/build/dialogue-u00-u21-safe-fixed-original \
  --output-dir work/build/dialogue-u00-u21-safe-names

.venv/bin/python scripts/build_ui_translation_patch.py \
  --file-build-dir work/build/dialogue-u00-u21-safe-names \
  --output-dir work/build/dialogue-u00-u21-safe-names-ui

.venv/bin/python scripts/build_dialogue_chapter_disc.py \
  --file-build-dir work/build/dialogue-u00-u21-safe-names-ui \
  --output-dir work/build/dialogue-u00-u21-safe-names-ui-disc
```

첫 명령은 다음을 모두 검사한다.

- 지원 원본 `START.BIN`, `ALLBIN.BIN`, `SLPS_019.58`의 SHA-256
- 기본 이름이 정확히 `시바` 2글리프와 `세이치로` 4글리프인지
- 34개 화자명 순서, 용어집 연결, 개별 6글리프와 전체 284바이트 한도
- alternate font 대상이 원본 zero tail인지
- MIPS instruction의 원본 word/immediate가 분석값과 정확히 일치하는지
- 선언된 글꼴·코드·문자열 범위 밖 변경이 없는지

두 번째 명령은 UI 4개와 필요한 alternate 한글 11자만 추가하고 보호 대상
56개를 바이트 단위로 유지한다. 마지막 명령은 `START.BIN`, `ALLBIN.BIN`,
`SLPS_019.58`을 원본
Mode 2/Form 1 트랙에 넣고 변경 sector의 EDC/ECC를 다시 계산한다. 완성
트랙에서 세 파일을 재추출해 입력 파일과 byte-for-byte로 비교한다.

## 실제 화면 검증

GUI 자동 조작은 하지 않는다. 사용자가 새 CUE를 콜드 부팅해 확인하는 항목은
다음과 같다.

1. 이름 설정 화면의 기본값이 성 `시바`, 이름 `세이치로`인지
2. 확정 후 다시 표시되는 주인공명이 잘리거나 한 글리프 밀리지 않는지
3. 대사창의 인물명과 아스라다·네메시스 등 시스템 화자명이 한국어인지
4. 이름이 바뀌는 이벤트에서 초상화·음성·분기 제어가 원래 시점에 유지되는지

2026-07-27 사용자 실행 검증에서 주인공 이름과 등록한 용어집 표기가 정상
출력되는 것을 확인했다. 이름 슬롯 재분할로 인한 글리프 잘림이나 다른
캐릭터 화자명 손상은 보고되지 않았다. 현재 판정은
`character-name-runtime-pass`다.

## 성 4칸·이름 4칸 구조 PoC

2026-07-29에는 검증된 2+4 패치를 기준으로 성과 이름을 각각 4글리프까지
수용하는 구조 PoC를 별도 빌드했다. 이 단계는 한글 입력 팔레트를 교체하는
작업이 아니라, 8글리프가 입력 화면·재표시·저장·불러오기 경로를 안전하게
통과할 수 있는지 확인하기 위한 비배포 실험이다. 기존 기본값
`시바 / 세이치로`, 로마자 이름 단계, 출신 선택 단계와 일본어 입력 팔레트는
그대로 둔다.

| 항목 | 4+4 PoC |
|---|---:|
| 글리프 record | 8개 × 74바이트 |
| 이름 bitmap 총량 | 592바이트, 148 dword |
| 성 scratch | `0x8002AD8C` |
| 이름 scratch | `0x8002AEB4` |
| live scratch 끝 | `0x8002AFDC` |
| 네 cache 시작 | `0x8002AFDC`, `0x8002B22C`, `0x8002B47C`, `0x8002B6CC` |
| cache 영역 끝 | `0x8002B91C` |
| 저장 슬롯 이름 시작 | `0x801F07B0`, `0x801F0EB0`, `0x801F15B0`, `0x801F1CB0` |

저장 슬롯마다 이름 bitmap 시작점을 기존보다 `0x50`바이트 앞당기면
592바이트 블록이 다음 슬롯 header 직전에 정확히 끝난다. 슬롯 stride
`0x700`과 header 위치는 바꾸지 않는다. unit 35의 저장 포인터와 복사 길이,
unit 39의 19개 복사 루프·네 cache·저장 슬롯 소비자, unit 40의 입력 한도와
scratch 포인터를 함께 수정했다.

메인 실행 파일에서는 화자명 문자열 영역의 검증된 zero tail 16바이트에
가상 글리프 코드 `0x4CE–0x4D5`를 고정 배열로 두고 성·이름 포인터가 각각
앞의 4개와 뒤의 4개를 가리키게 했다. 해당 배열을 덮던 초기화 store만
NOP 처리했으며 로마자 이름 초기화 블록
`0x80039F24–0x80039F58`은 byte-for-byte로 유지한다.

```bash
.venv/bin/python scripts/build_name_4x4_poc.py \
  --file-build-dir work/build/dialogue-all-reviewed-font-text-2026-07-29 \
  --output-dir work/build/dialogue-all-reviewed-font-text-name-4x4-poc-2026-07-29

.venv/bin/python scripts/build_dialogue_chapter_disc.py \
  --file-build-dir work/build/dialogue-all-reviewed-font-text-name-4x4-poc-2026-07-29 \
  --output-dir work/build/disc1-name-4x4-poc-2026-07-29
```

Expected Writes 검사는 `ALLBIN.BIN` 141바이트와 `SLPS_019.58` 110바이트만
변경됐음을 확인했다. `START.BIN`은 변경하지 않았다. IDA Pro에서 저장·cache
복사 루프와 로마자 초기화 블록을, Ghidra에서 unit 35·39·40과 메인 실행
파일의 주소 참조를 다시 대조했다. 전체 181개 자동 테스트와 완성 트랙의
세 파일 재추출 비교도 통과했다.
