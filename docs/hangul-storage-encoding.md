# 한국어 글리프 저장 공간과 인코딩 전략

## 결론

전체 한국어 글리프는 Disc 1 Track 1 말미의 미사용 150섹터에 전용 폰트 팩으로
저장하고, 런타임 RAM에는 한 화면 또는 한 텍스트 블록에서 필요한 글리프만
올리는 **화면 단위 캐시**를 채택한다. 이 저장 공간 결정은 유지한다.

반면 텍스트 스트림의 한글 토큰을 `0x5xxx` 또는 `0x7xxx` 같은 고상위 대역으로
직접 운반하는 방식은 폐기한다. 대표 텍스트 구간에는 해당 값이 없었지만, 실제
엔진은 렌더러 직전에 블록별 표시 구조와 리맵 표를 거친다. 따라서 정적 corpus의
미사용 대역은 최종 글리프 토큰으로 안전하다는 뜻이 아니다.

후속 전략은 엔진이 이미 받아들이는 작은 로컬 토큰을 쓰고, 그 토큰이 가리키는
리맵 표 또는 표시 버퍼 항목을 한글 캐시 슬롯으로 연결하는 방식이다. 자세한
작업 단위는 [`docs/remap-table-strategy.md`](remap-table-strategy.md)에 둔다.

## 왜 전상주가 아닌가

Galmuri11 사용 글꼴의 전체 2,350자를 게임 포맷으로 저장하면 다음 크기가
필요하다.

| 대상 | 계산 | 크기 |
|---|---:|---:|
| 한글 2,350자만 | `2350 * 74` | `0x2A74C` bytes |
| 기존 12비트 슬롯 전체 | `4096 * 74` | `0x4A000` bytes |
| 기존 `0x000..0x4FF` 보존 + 2,350자 | `(0x500 + 2350) * 74` | `0x4194C` bytes |

대사 시점 RAM 덤프에서 확인한 큰 0 채움 구간은 최대 `0xD524` bytes
(`0x800B9ADC..0x800C6FFF`)이며, 전체 한글 2,350자를 한 번에 둘 수 없다.
`0x80185000`부터의 보조 폰트 베이스 경로도 대사 시점에는 이미 데이터가 있어
전용 상주 영역으로 사용할 수 없다.

반면 본문 한 화면은 원본 기준 2줄 30칸이며, 한 화면의 최악 글리프 수를 30자로
잡아도 `30 * 74 = 0x8AC` bytes에 불과하다. 256자 캐시는 `0x4A00` bytes,
512자 캐시는 `0x9400` bytes로, 현재 확인된 대사 시점 0 채움 구간 안에 들어간다.
따라서 저장은 전량, 활성 RAM은 화면 단위 캐시로 분리하는 쪽이 공간 대비 구현
위험이 낮다.

## 디스크 저장 위치와 형식

Track 1은 255,961 raw sector이고, 마지막 데이터 파일 `MOVIE2.STR`은
`LBA 221486`에서 `70,297,600`바이트를 차지해 `LBA 255811`에서 끝난다.
따라서 `LBA 255811..255960`의 150섹터, 즉 `150 * 2048 = 307,200`바이트
user data 영역이 데이터 트랙 안에 남아 있다.

이 구간은 Track 1 내부에 있으므로 멀티트랙 CUE의 뒤쪽 CDDA 트랙 시작 LBA를
밀지 않는다. 또한 `4096 * 74 = 303,104`바이트인 12비트 글리프 슬롯 전체
테이블도 들어가므로, 전체 Galmuri11 2,350자 폰트 팩과 작은 헤더를 담기에
충분하다.

폰트 팩에는 Galmuri11에서 생성한 14x14, 3bpp, 74바이트 글리프를 저장한다.

- 글리프 원본: `Galmuri11 Regular`, TTF 12px 래스터, `x=1`, `y=0`
- 실제 잉크 합집합: 14×14 셀의 `(1,1)..(11,11)`
- 글리프 포맷: 기존 본문과 같은 14x14, 3bpp, 74바이트
- 글리프 값: 본문 기준 켜진 픽셀 `1`, 배경 `0`
- 저장 순서: 빌드가 생성하는 한글 문자표 순서
- 위치: Disc 1 Track 1 `LBA 255811..255960`
- 배포: 원본 이미지 전체가 아니라 차이 패치에 포함

최초 구현에서는 전 2,350자를 저장할 수 있게 설계하되, 빌드 인코더는 실제 번역에
사용된 음절만 캐시 매니페스트에 넣는다. 번역문에 Galmuri 문자표 밖의 한글
음절이나 매핑 없는 문자가 있으면 빌드 에러로 처리한다.

## 폐기한 텍스트 인코딩

`ALLBIN.BIN + 0x54..0x2A800` 대표 텍스트 구간의 u16 토큰을 집계한 결과
`0x5xxx`와 `0x7xxx` 대역은 등장하지 않았다. `0x4xxx`와 `0x6xxx`에는 각각
`0x4000`, `0x6000`이 등장하므로 처음에는 `0x5xxx`를 한글 표식 후보로 삼았다.

| 대역 | 대표 텍스트 구간 출현 | 판정 |
|---|---:|---|
| `0x4xxx` | 27 | 사용하지 않음 |
| `0x5xxx` | 0 | 화면 검증에서 폐기 |
| `0x6xxx` | 14 | 사용하지 않음 |
| `0x7xxx` | 0 | 화면 검증에서 폐기 |

실험 결과는 다음과 같다.

```text
0x5000..0x5011: 화면에 한글 대신 한자 司馬가 반복 표시됨
0x7000..0x7011: 원본 대사 RAM에는 남지만 렌더러 직전에서 한글이 사라짐
```

`0x5xxx` 반례는 해당 대역이 이름/변수 표시 또는 기본 이름 확장 경로와 충돌함을
보여 준다. `0x7xxx` 반례는 원본 대사 RAM의 값이 렌더러까지 그대로 전달되지
않고, 블록별 리맵/표시 버퍼 계층에서 해석된다는 점을 보여 준다.

## 새 런타임 방향

렌더러의 글리프 주소 계산 직전에는 다음 흐름이 있다. 이 위치의 말단 훅은
고상위 토큰 운반에는 너무 늦다.

```text
0x80032804: andi v1, v1, 0x0FFF
0x80032808..0x8003281C: v1 * 74 계산
0x8003281C: a1 = font_base + v1 * 74
```

다음 PoC는 이 말단 계산보다 앞선 변환 계층을 추적한다. 관찰된 핵심 주소는
다음과 같다.

| 항목 | 주소 |
|---|---:|
| 원본 첫 대사 RAM | `0x800A8054` |
| 렌더러 직전 표시 구조 후보 | `0x8001425A` |
| 리맵 기준 구조 후보 | `0x8001426C` |
| 리맵 기준 포인터 저장 위치 | `0x80061158` |

후속 PoC의 목표는 다음 세 가지다.

1. `ALLBIN.BIN + 0x54`의 토큰들이 표시 구조와 리맵 표로 변환되는 생산자 코드를
   찾는다.
2. 첫 대사 34토큰에 대해 원본 토큰, 표시 구조 토큰, 리맵 출력값의 대응을 남긴다.
3. 한글 18자만 작은 로컬 토큰으로 배정하고, 리맵 표 또는 표시 버퍼를 한글 캐시
   슬롯으로 연결한다.

폐기된 고상위 토큰 훅의 재현 기록은
[`docs/cache-hook-poc.md`](cache-hook-poc.md)에 보존한다.

## 남은 미확정 사항

- 한글 캐시 RAM의 최종 주소, 수명, 초기화 시점
- 텍스트 블록 경계, 리맵 표 경계, 캐시 매니페스트를 어떤 단위로 생성할지
- 엔진 네이티브 로컬 토큰을 어느 범위에서 회수할지
- 글리프 팩 읽기를 기존 파일 로더에 얹을지, 직접 CD 읽기로 처리할지
- Mode 2 Form 1 EDC/ECC 재계산을 포함한 실기용 빌드 경로
